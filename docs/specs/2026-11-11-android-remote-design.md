# minibot 安卓端与中继 设计文档

日期：2026-11-11　状态：待批准
关系：扩展 `2026-11-07-minibot-core-design.md`。核心设计第 2 节把"中继、手机端 App"列为第一版非目标，第 4.1 / 4.2 节为二者预留了接口和"另一套配对令牌"；本文就是那份"届时再设计"。两者冲突时，本文只覆盖手机端与中继相关部分，其余仍以核心设计为准。

## 1. 意图与动机

用户经常**人在外面**，电脑（家里或办公室）开着 minibot 跑任务。希望用手机继续和 bot 对话、看它在电脑上干活的进度、在 bot 请求危险操作时**及时收到提醒并批准或拒绝**。

"远程控制电脑"在这里的含义是：**通过 bot 干活**。手机是 minibot 的另一个前端，活仍然由电脑上的内核执行。不做远程桌面（看屏幕、点鼠标）。

连接方式：主要经由**用户自己的服务器**做中继；在同一局域网时直连电脑，更快，且服务器挂掉时在家仍可用。

## 2. 目标 / 非目标 / 反目标

**目标**
- 一个自用的安卓 APK（直接安装，不上架）。
- 手机端功能：选 bot；聊天（含发图片）；中断正在进行的回复；处理审批（批准 / 拒绝 / 总是允许）；翻看历史；新建、重命名、删除对话。
- 收到审批请求、任务结束（回复完成 / 失败）时弹系统通知，App 不在前台也能收到。
- 一个自带的中继程序，部署在用户自己的服务器上。
- 局域网直连，与中继走同一套加密协议；App 先试直连，不通再走中继。
- 扫码配对；电脑上能看到已配对的手机并撤销。

**非目标（这一版不做）**
- 远程桌面 / 屏幕查看 / 键鼠操控。
- 手机上修改配置：模型服务与 API Key、bot 设置（人设、模型、审批模式、命令白名单、工作目录）、长期记忆编辑、初始化流程。这些留在电脑上做。
- iOS、平板专用布局、上架应用商店。
- 谷歌 FCM 或任何第三方推送服务。
- 一台手机同时连多台电脑（数据结构不排斥，界面不做）。
- 局域网内自动发现（mDNS 等），靠配对时记下的地址即可。
- 手机 App 单独的应用锁（指纹 / 密码）。
- 电脑开机自启。

**反目标（即使能跑也算失败）**
- 中继服务器能看到对话内容、审批内容或 API Key，或者能伪造手机向电脑下指令。中继被攻破 ≠ 电脑被控制。
- 依赖 minibot 自己的账号、我方云服务或谷歌服务。
- 手机能调用"非目标"里列出的配置类接口——**不是界面上藏起来，而是电脑端直接拒绝**。
- 现有 `127.0.0.1` 本机接口的安全边界被放宽（比如改成监听 `0.0.0.0`、放松 `Host`/`Origin` 校验）。
- 审批逻辑出现第二份：手机与桌面的审批都必须落到内核同一个 `respondApproval`。
- 手机端文案、颜色与桌面端各写一份、各自漂移。

## 3. 约束

- 继承核心设计第 3 节：TypeScript、依赖尽量少、不引入需要原生编译的 Node 依赖。
- 电脑端加密只用 Node 内置 `node:crypto`（X25519、ChaCha20-Poly1305、SHA-256、HKDF 都有），不加原生依赖。
- 手机端界面遵循 `.claude/CLAUDE.md` 的设计语言：黑白灰语义 token、`recipes.ts`、`src/ui/` 浮层组件；文案只有简体中文，集中在 `i18n.ts`。
- 电脑休眠时手机连不上，属预期；手机端要能清楚显示"电脑离线"。
- 国产安卓系统会杀后台：只能尽量（前台服务 + 引导用户加电池优化白名单），不保证。

## 4. 做法比较（已选定）

中继与电脑端三种做法都一样，区别只在安卓 App：

| 做法 | 说明 | 取舍 |
|---|---|---|
| **A. WebView 外壳 + 复用 React 界面 + 少量 Kotlin（选定）** | Capacitor 打包；界面复用 `apps/renderer` 的 token、recipes、i18n、对话 hook，另做手机布局；Kotlin 前台服务负责后台常驻连接、加解密和通知 | 大部分是 TS，两端视觉与文案一致；代价是 Kotlin↔网页的桥接，WebView 手感略逊原生 |
| B. 纯原生 Kotlin + Jetpack Compose | 整个 App 用 Kotlin 重写 | 后台与手感最好；多一套完整界面技术，文案和设计要两边维护，违背"单一语言、移动部件少" |
| C. React Native | — | 仍要重写界面、仍要原生后台服务，两头的缺点都有 |

PWA 被排除：无法后台常驻连接，收不到审批通知。
通知方式选定**后台常驻连接**（前台服务 + 常驻通知），不用 FCM：不依赖谷歌，代价是一点耗电和常驻通知栏。

用户选择：做法 A；自有服务器做中继；后台常驻通知；功能范围为"聊天 + 审批 + 对话管理"；局域网直连第一版就做；电脑端关窗口缩到托盘（不做开机自启）；手机不加应用锁。

**我替你定的（请过目）**：Noise 协议做端到端加密；扫码配对、配对码 5 分钟一次性；通知里不放"批准"按钮、必须进 App 操作；手机端只能调用白名单接口（服务端强制）；没有系统密钥库时手机功能不可用；中继自身不做 TLS、推荐 Caddy 反代；最低 Android 8.0。

## 5. 架构总览

```
 手机 App                              用户服务器                     电脑（Electron 主进程）
┌──────────────────────┐            ┌──────────────┐             ┌────────────────────────────┐
│ WebView：手机界面     │            │  relay       │             │ 内核 Kernel                 │
│  (React, 复用 renderer)│           │  只转发密文   │             │   ▲                        │
│        ▲ 桥接(明文)   │            │  不存数据     │             │   │ 同一套路由/审批          │
│ Kotlin 前台服务        │  wss  ───► │              │ ◄─── wss    │ 远程网关 RemoteGateway      │
│  连接/加解密/通知      │            └──────────────┘             │  加解密、白名单、设备管理    │
│                      │ ── 局域网直连（同一加密协议）──────────────►│  局域网监听端口              │
└──────────────────────┘                                          │ 原有 127.0.0.1 服务（不变）  │
                                                                  └────────────────────────────┘
```

- 电脑和手机都**主动连出**到中继，电脑不需要公网 IP、不需要在路由器上开端口。
- 端到端加密在手机的 Kotlin 服务与电脑的远程网关之间完成；中继和 WebView 之外的任何中间环节都只见密文。
- 远程网关解密后，把请求交给与现有 HTTP 路由**同一份**处理逻辑，事件也从内核同一个 `kernel.on` 订阅推出。

## 6. 组件设计

### 6.1 中继 `packages/relay`

- 独立的 Node 程序（TS），依赖只有 `ws`。单个 WebSocket 端点，例如 `/v1`。
- **接入鉴权（防白嫖带宽，不是安全边界）**：中继配置一个"中继口令"，连接时首条消息携带。口令错误立即断开。真正的安全由端到端加密保证，中继口令泄露最多让别人用你的带宽。
- **路由**：每台电脑有一个长期 X25519 密钥对；路由 ID = 电脑公钥的 SHA-256 前 16 字节（hex）。电脑以 `role: pc, routeId` 注册；手机以 `role: phone, routeId, sessionId`（手机每次连接随机生成）接入。中继把手机的帧原样转给对应电脑，并在帧外加 `sessionId` 以区分多台手机；电脑回帧时带 `sessionId`，中继转回对应手机。
- 同一 `routeId` 的电脑重复注册：新的顶替旧的（电脑重启、网络切换）。电脑不在线时，手机收到中继的 `pc_offline` 提示，等待电脑上线时收到 `pc_online`。
- 不存任何数据，不写日志正文；只记连接数、错误。单帧上限（例如 8 MB，覆盖图片附件），超限断开。基本限流：每 IP 每分钟的连接次数。
- 心跳：中继每 25 秒 ping，60 秒无响应断开，适配移动网络 NAT 超时。
- **TLS**：中继本身只说明文 `ws`，监听本机端口；推荐用 Caddy 反向代理自动签证书，对外 `wss://`。提供 `Dockerfile` 与一份 Caddy 示例配置，以及不用 Docker 的 `node relay.js` 方式；部署文档写在 `packages/relay/README.md`。
- 即使用户只用 `ws://`（无 TLS），端到端加密仍保证内容安全；但元数据（谁在何时连）可见。界面上对 `ws://` 给出提示，不禁止。

### 6.2 加密协议（电脑 ↔ 手机）

使用 Noise Protocol Framework，原语：`25519_ChaChaPoly_SHA256`。

- **配对握手**：`Noise_XXpsk3`，psk 为二维码里的一次性配对密钥（32 字节随机）。完成后双方得到对方长期公钥，各自存档。配对密钥 5 分钟过期、用一次即作废。
- **日常握手**：`Noise_KK`（双方已知对方公钥）。握手成功即证明对方是已配对设备；电脑端校验手机公钥在"已配对设备"列表且未撤销。
- 握手后用 Noise 传输态加解密每条消息，nonce 由协议计数，重放与乱序自然被拒。
- 直连与中继用**完全相同**的握手和帧格式，只是承载的 WebSocket 不同。
- 实现要求：优先使用成熟的 Noise 实现；若手写，必须通过 Noise 官方测试向量（cacophony / snow 的 vectors），并且 TS 与 Kotlin 两端用同一份互通测试向量。不自创原语。
- Kotlin 端 X25519 / ChaCha20-Poly1305 的来源（Tink、BouncyCastle、或系统提供）由实现者定，见第 9 节。

### 6.3 应用层消息（加密信道之内）

明文是 JSON，三类：

```jsonc
// 手机 → 电脑：调用接口
{ "t": "req", "id": 17, "method": "POST", "path": "/api/threads/abc/messages", "body": { ... } }
// 电脑 → 手机：接口结果
{ "t": "res", "id": 17, "status": 200, "body": { ... } }          // 附件这类二进制用 base64 字段
// 电脑 → 手机：内核事件（与本机 WS 推送的 KernelEvent 完全相同）
{ "t": "evt", "event": { "type": "approval_request", ... } }
// 手机 → 电脑：与本机 WS 相同的控制消息
{ "t": "ctl", "msg": { "type": "approval", "id": "...", "approve": true, "always": false } }
{ "t": "ctl", "msg": { "type": "abort", "threadId": "..." } }
// 电脑 → 手机：握手后首条，等同本机 WS 的 ready（此后再读状态不会漏事件）
{ "t": "ready", "pcName": "..." }
```

- 断线重连后客户端按现有 `onOpen` 的逻辑重新拉取状态，沿用 `86dcf30` 里"重连同步"的做法。
- 事件不做离线缓存：手机断开期间的事件靠重连后拉取补齐（待审批列表有 `/api/approvals`）。

### 6.4 电脑端：远程网关（`packages/core/src/remote/`）

- **路由抽离**：把 `server/routes.ts` 的 `route(...)` 改造成与传输无关的分发函数（输入 method、path、query、body，输出 status + JSON 或字节），本机 HTTP 服务与远程网关都调用它。本机服务行为不变。
- **接口白名单（服务端强制）**：远程来源只放行下列接口，其余一律返回 403（code `remote_forbidden`）：
  - 读：`GET /api/state`、`/api/running`、`/api/approvals`、`/api/search`、`/api/bots/:id/threads`、`/api/threads/:id/messages`、`/api/threads/:id`、`/api/threads/:id/usage`、`/api/attachments/:id`
  - 写：`POST /api/bots/:id/threads`（新建对话）、`POST /api/threads/:id/messages`（发消息，含图片）、`PATCH /api/threads/:id`（重命名）、`DELETE /api/threads/:id`、`POST /api/threads/:id/retry`
  - 控制消息：`abort`、`approval`
  - 明确不放行：`/api/settings`、`/api/providers*`、`/api/onboarding`、`/api/memory*`、`/api/bots/:id` 的 PATCH、`/api/presets`、`/api/approvals/log`、`/api/threads/:id/compact`、`/api/threads/:id/context` 等。
  - 白名单是一张表，放在一处，有单元测试逐条覆盖"放行 / 拒绝"。
  - `GET /api/state` 返回内容若含 provider 配置等，需确认不含 Key（核心设计已保证 Key 不出内核，此处测试再验一次）。
- **"总是允许"**：手机上的"总是允许"与桌面同义（加入该 bot 命令白名单）。它会改变 bot 配置，但属于审批动作的一部分，放行。
- **中继连接**：内核启动时，若已配置中继且有已配对设备，主动连中继并注册；断线指数退避重连（1s 起，上限 60s）。
- **局域网监听**：独立的 HTTP 服务（**不是**现有 127.0.0.1 那个），监听 `0.0.0.0:<端口>`，默认端口固定（例如 47821，可改），只接受 `/v1` 的 WebSocket，只说加密协议；其余请求 404。有已配对设备且用户开启"局域网直连"时才监听。Windows 首次监听会弹防火墙提示，属正常，文档说明。
- **设备管理**：已配对设备存于数据目录（`devices.json`，原子写）：设备名、手机公钥、配对时间、最后在线时间、来源（直连/中继）。撤销 = 删除记录 + 立即断开该设备的所有会话。电脑长期私钥用现有 `KeyCrypto`（系统密钥库）加密落盘，与 API Key 同等待遇。
- 远程来源的操作在日志里标记来源设备名，便于事后查。
- **没有系统密钥库时**（如 Linux 下 safe storage 退回 `basic_text`，`SecretStore.canPersist()` 为假）：手机功能整体不可用，"手机"页显示原因，不以弱保护存电脑私钥，也不每次启动换密钥。（实现者判断：与 API Key 的处理一致。）
- 手机的长期私钥存在 Android Keystore 包裹的密钥下，**不**绑定用户验证，以便后台服务自动重连。

### 6.4.1 电脑端：关窗口缩到托盘

用户选定。现在 `apps/desktop/src/main.cts` 在 `window-all-closed` 时 `app.quit()`，关窗口远程就断了。改为：

- **有已配对设备时**，关闭主窗口只是隐藏，程序与内核继续运行；没有已配对设备时保持现在的行为（直接退出）。
- 托盘图标（品牌符号，与 `docs/brand` 一致），菜单：打开 minibot / 退出。退出才真正结束进程。
- 第一次因此缩到托盘时，弹一次系统通知说明"minibot 仍在后台运行，可从托盘退出"。
- 不做开机自启。

### 6.6 安卓 App

**目录**：`apps/mobile`（手机界面的 Web 源码，Vite + React）与 `apps/mobile/android`（Capacitor 生成的原生工程，含 Kotlin 前台服务）。是否把共用代码抽成 `packages/ui` 由实现者定，原则是**手机端不复制粘贴桌面端文件**，通过 import 复用。

**复用**：`styles.css` 的 token、`ui/recipes.ts`、`ui/` 浮层组件、`i18n.ts`、`brand/Logo.tsx`、`main/` 里的 `useConversation`、`ApprovalCard`、`Transcript`、`Composer`、`useComposerImages`（按需调整为可在窄屏使用）。

**API 抽象**：现有 `apps/renderer/src/api.ts` 写死了 `fetch('http://127.0.0.1:…')` 与 `new WebSocket(...)`。改为注入一个"传输"接口（`request(method, path, body)` + 事件订阅 + `send(ctl)` + `onOpen`）：桌面用现有本机实现，手机用"原生桥接"实现。`createApi` 的方法签名不变，上层 hook 与组件不用改。

**Kotlin 前台服务**（App 唯一的原生逻辑）：
- 持有到电脑的连接：配对后先试二维码里记下的局域网地址（每个地址 1.5 秒超时），都不通再连中继；连上后保持。网络变化（Wi-Fi ↔ 移动数据）时重新走一遍选择。
- 做 Noise 握手与加解密；与 WebView 之间通过 Capacitor 插件传**明文** JSON（同一进程内）。
- 常驻通知显示连接状态（"已连接电脑 · 中继" / "电脑离线" / "正在重连"）。
- 收到 `approval_request` 事件：发一条高优先级通知"<bot 名> 请求批准：<操作摘要>"，点开进入 App 对应对话的审批卡片。收到 `turn` 由 running 变 idle：发一条普通通知"<bot 名> 已完成"。App 在前台且正停在该对话时不发。
- 通知里**不放**"批准"按钮（锁屏可见、易误触），必须进 App 操作。
- 首次启动引导：请求通知权限；引导把 App 加入电池优化白名单（跳转系统设置）。
- 前台服务类型使用 Android 14 起要求的 `foregroundServiceType`（具体选 `remoteMessaging` 还是 `dataSync` 由实现者按当前政策定）。
- 用户可在 App 里"断开并停止后台"，此时停止前台服务、不再收通知。

## 7. 安全要点汇总

| 威胁 | 应对 |
|---|---|
| 中继被攻破 / 运营方窥探 | 端到端 Noise 加密；中继只见密文与路由 ID |
| 有人冒充手机连电脑 | `Noise_KK` 要求手机持有已配对私钥；电脑校验设备列表 |
| 有人冒充电脑骗手机 | 手机校验电脑公钥（配对时记录） |
| 二维码被偷拍 | 配对密钥一次性、5 分钟过期；新配对的设备会出现在电脑的已配对列表里 |
| 手机丢失 | 电脑上撤销该设备，立即断开。不加应用锁（用户决定），依赖手机自身锁屏 |
| 远程改配置 / 偷 Key | 服务端接口白名单；Key 本就不出内核 |
| 局域网内他人扫端口 | 局域网端口只说加密协议，未配对无法完成握手 |
| 放宽本机接口 | 本机 127.0.0.1 服务完全不动，远程走独立监听 |

## 8. 测试

- **协议**：Noise 官方测试向量；TS 与 Kotlin 共用一份互通向量（握手 + 若干条传输消息）。
- **白名单**：每个路由一条放行 / 拒绝测试；新增路由默认拒绝（白名单外即拒）。
- **网关**：用假传输跑通配对、日常握手、请求转发、事件推送、撤销即断开、过期 / 重用配对密钥被拒、未知公钥被拒。
- **中继**：注册、转发、多手机 `sessionId` 区分、电脑顶替注册、`pc_offline/pc_online`、口令错误断开、超大帧断开。
- **局域网监听**：只接受 `/v1` 升级；HTTP 其他路径 404；未开启时不监听。
- **回归**：本机服务现有测试全部通过（路由抽离不改行为）。
- 安卓端：Kotlin 单测覆盖加解密与重连状态机；手动验证清单（锁屏通知、切网络、杀后台后的恢复、国产系统电池优化）。
